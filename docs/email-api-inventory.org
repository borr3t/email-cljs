* About this document
This is the verified inventory of the surface that email-cljs wraps: SMTP sending through
nodemailer, IMAP access (including IDLE) through imapflow, and message parsing through
mailparser, plus the protocol/MIME semantics the ClojureScript API has to model. It is
research only; implementation happens in phases 2-4 and the live smoke in phase 5.

*Product constraint that shapes everything below:* the finished library is ClojureScript at
the surface — no =^js= hints, no interop at call sites, kebab-case keyword maps in and out,
promesa promises for every async operation, a core.async channel for the IMAP IDLE watcher —
and its only runtime npm dependencies are the three wrapped packages. Every JS-facing detail
inventoried here (Buffers, Maps, Sets, streams, EventEmitters, camelCase option names) is
therefore something a *binding namespace* has to absorb (section 9), never something the
caller sees.

** Reading conventions
- Wire/option names are given verbatim (camelCase, as the packages spell them); the kebab-case
  keyword translation lives in section 14.1. IMAP flags are given with their backslash
  (=\Seen=); in ClojureScript strings that is ="\\Seen"=.
- "Scope" column values: =core= (the library implements it in phases 2-4), =read=
  (read-only helper), =later= (inventoried, deferred past phase 4), =none= (deliberately not
  exposed, with the reason).
- Sizes are bytes; times are milliseconds unless the package says otherwise; IMAP
  =uidValidity= / =modseq= are JS BigInt (imapflow) — section 14.2 says what they become.
- "The smoke account" means the catch-all account described in section 15; its credentials
  live in =~/.secrets/borret.txt= and are never reproduced here.

** 1.4 Shared address-object shape [DTS addressparser][SRC mailparser][PROBE]
All three packages describe a mailbox as ={name: string, address: string}= and a group as
={name, group: [...]}=:
- nodemailer =addressparser(str, {flatten?})= returns =Address[]= where a mailbox is
  ={name, address}= (either may be the empty string) and a group is ={name, group: Address[]}=
  (nested groups are flattened, RFC 5322 forbids nesting) [DTS addressparser/index.d.ts].
- nodemailer =MimeNodeAddress= (input side) is ={name?, address?, group?}=; address input is
  =string | MimeNodeAddress | (nested) arrays= and comma-separated strings are split
  [DTS mime-node].
- imapflow ENVELOPE addresses are =MessageAddressObject {name?, address?}= (no groups; the
  server already flattened them; since 1.7.2 a NIL host no longer invents an address) [DTS types].
- mailparser wraps a header's list into ={value: Address[], html: string, text: string}= [SRC processHeaders][PROBE].
- postal-mime: =Mailbox {name, address}= / group ={name, group: Mailbox[]}= [DTS].
Consequence for the library: ONE kebab shape ={:name .. :address ..}= (and ={:name .. :group [..]}=
for groups) everywhere (14.3).

* 2. nodemailer surface (SMTP)
** 2.1 =createTransport(options[, defaults])= [DTS nodemailer.d.ts][DOC smtp]
Returns a =Mail= instance ("transporter"). Overloads select the transport by option:
={pool: true}= -> pooled SMTP, ={streamTransport: true}= -> stream, ={jsonTransport: true}=
-> JSON, ={sendmail: true}= -> sendmail, ={SES: {...}}= -> SES, a =Transport= object -> plugin,
otherwise (object or =smtp://= / =smtps://= URL string) -> single-connection SMTP.
=defaults= is a =MailDefaults= (= =SendMailOptions=) merged into every message (headers merged
one by one).

** 2.3 Authentication [DTS SMTPTransportAuthOptions][DOC smtp]
={type?: 'login' (default) | 'oauth2', user, pass, method?, options?, service?}=; OAuth2 adds
=accessToken=, =expires=, =clientId=, =clientSecret=, =refreshToken= … (XOAuth2Options).
- Password login: nodemailer picks the first server-advertised SASL mechanism in the order
  PLAIN, LOGIN, CRAM-MD5 (=authMethod= / =auth.method= forces one). The task brief's "auth
  type LOGIN" is the *type* (=type: 'login'=, the default, i.e. password auth), not the SASL
  mechanism; =AUTH LOGIN= the mechanism is selected only if PLAIN is not advertised or
  =authMethod: 'LOGIN'= is set. [DOC smtp "Login"][SRC smtp-connection _authMethod]
- Failures: EAUTH with =command= naming the mechanism (=AUTH PLAIN= / =AUTH LOGIN= /
  =AUTH CRAM-MD5= / =AUTH XOAUTH2=) and =response= / =responseCode= (typically 535) (8.1).
- Per-message =auth= override exists (=SendMailOptions.auth=) — none.

** 2.5 =sendMail= result for SMTP (=SMTPSentMessageInfo=) [DTS smtp-transport + smtp-connection][DOC index "Response object"][SRC smtp-transport send]
| Field            | Type            | Meaning |
|------------------+-----------------+---------|
| =envelope=       | ={from: string|false, to: string[]}= | what was actually used for MAIL FROM / RCPT TO (cc+bcc merged into =to=) |
| =messageId=      | string with angle brackets | the Message-ID header value |
| =accepted=       | string[]        | recipients the server accepted at RCPT TO (and not later rejected per-recipient at DATA for LMTP) |
| =rejected=       | string[]        | recipients refused at RCPT TO |
| =rejectedErrors= | =NodemailerError[]= | one per rejected recipient (=recipient=, =response=, =responseCode=, =command: 'RCPT TO'=); present only if non-empty |
| =pending=        | string[]        | LMTP only |
| =response=       | string          | final server reply to DATA, e.g. ="250 2.0.0 Ok: queued as ABC123"= |
| =ehlo=           | string[]        | EHLO capability lines (e.g. =PIPELINING=, =SIZE 52428800=, =8BITMIME=, =SMTPUTF8=, =AUTH PLAIN LOGIN=, =DSN=) |
| =envelopeTime= =messageTime= | ms  | timings |
| =messageSize=    | bytes           | encoded size streamed |
Partial success rule: the promise *resolves* as long as at least one recipient was accepted;
it *rejects* with EENVELOPE "Can't send mail - all recipients were rejected" (carrying
=rejected= / =rejectedErrors=) only when every recipient was refused [DOC index][SRC 1605-1616].
The library therefore has to surface =:rejected= on the *success* value (14.3) — a caller who
wants all-or-nothing must check it.

* 3. SMTP protocol essentials for the error taxonomy
** 3.1 Envelope vs headers [RFC 5321/5322][DOC smtp/envelope]
- The *envelope* is =MAIL FROM:<return-path>= + one =RCPT TO:<addr>= per recipient; it is
  what the server delivers to and where bounces go. The *headers* (=From:=, =To:=, =Cc:=,
  =Bcc:=) are what recipients see. nodemailer derives the envelope from =from= (falling back
  to =replyTo= then =sender= for MAIL FROM) and =to+cc+bcc= (deduplicated), and strips the
  =Bcc:= header from the transmitted message (SMTP transport; the stream transport keeps it).
- =envelope: {from, to, cc, bcc, ...}= overrides it; extra keys are copied through
  (=size=, =dsn=, =use8BitMime=, =requireTLSExtensionEnabled=) [DTS SMTPEnvelope].
- A =raw= message *requires* an explicit envelope: nodemailer does not parse addresses out
  of raw source [DOC custom-source].
- Address forms accepted anywhere: ="a@b"=, ="Name <a@b>"=, ='"Doe, John" <a@b>'=,
  ={name, address}=. Unquoted commas in display names are a hazard (12.1). IDN domains are
  punycoded automatically when the local part is ASCII; non-ASCII local parts trigger
  =SMTPUTF8= (only if advertised; else the server's 550/553 surfaces as EENVELOPE) [DOC addresses].

** 3.2 Reply codes as nodemailer exposes them [DOC errors][SRC _formatError]
=err.responseCode= is the leading 3-digit number of =err.response= (the raw reply line);
=err.command= names the phase (=CONN=, =EHLO=, =AUTH PLAIN=, =MAIL FROM=, =RCPT TO=, =DATA=,
=RSET=, =API= for client-side validation). Codes the library must classify (=util/smtp-code-class=
does 1xx-5xx by first digit; =util/smtp-retryable?= = 4xx):
| Code | Where              | Meaning                                         | Retryable |
|------+--------------------+-------------------------------------------------+-----------|
| 220  | greeting           | service ready                                   | -         |
| 221  | QUIT               | closing                                         | -         |
| 235  | AUTH               | authentication successful                       | -         |
| 250  | EHLO/MAIL/RCPT/DATA end | OK (=response= of a successful send)        | -         |
| 251/252 | RCPT            | will forward / cannot VRFY but accepts          | -         |
| 354  | DATA               | start mail input                                | -         |
| 421  | any                | service not available, closing (nodemailer maps to ECONNECTION) | yes |
| 450  | RCPT               | mailbox unavailable (greylisting is usually 450/451) | yes    |
| 451  | any                | local error / greylisted                        | yes       |
| 452  | RCPT/DATA          | insufficient storage / too many recipients      | yes       |
| 454  | AUTH               | temporary authentication failure                | yes       |
| 500-504 | any             | syntax / not implemented / bad sequence         | no        |
| 530  | MAIL               | authentication required                         | no (auth) |
| 535  | AUTH               | credentials invalid (EAUTH)                     | no        |
| 538  | AUTH               | encryption required for mechanism               | no        |
| 550  | RCPT/DATA/MAIL     | mailbox unavailable / relay denied / policy     | no        |
| 551  | RCPT               | user not local                                  | no        |
| 552  | DATA               | exceeded storage / message too big              | no        |
| 553  | RCPT/MAIL          | mailbox name not allowed (syntax; SMTPUTF8 refused) | no    |
| 554  | DATA/greeting      | transaction failed / no service                 | no        |
| 555  | MAIL/RCPT          | parameters not recognized                       | no        |
Enhanced status codes (=5.7.8=, =2.0.0=) ride in =response= text; nodemailer does not parse
them (only custom-auth handlers see =code=). The library keeps =:response= verbatim.

** 3.3 465 implicit TLS vs 587 STARTTLS [DOC smtp][DTS][RFC 8314]
| Port | Mode                       | nodemailer                                              | imapflow analogue |
|------+----------------------------+---------------------------------------------------------+-------------------|
| 465  | implicit TLS ("SMTPS")     | =secure: true= (auto when port 465 and =secure= unset); TLS handshake before the greeting; STARTTLS never used | port 993 =secure: true= (auto when port 993 and =secure= unset) |
| 587  | submission + STARTTLS      | =secure: false= (default); cleartext EHLO, then STARTTLS if advertised (unless =ignoreTLS=); =requireTLS: true= to refuse cleartext fallback | port 143 =secure: false=; =doSTARTTLS: true= to require the upgrade, =false= to forbid it |
| 25   | MTA relay                  | as 587; usually blocked outbound by ISPs                | -                 |
The smoke account is =465= with TLS (and IMAP =993= with TLS): the library's config maps
=:smtp {:host :port 465 :tls? true}= to =secure: true= and =:imap {:port 993 :tls? true}= to
=secure: true=. TLS errors: nodemailer =ETLS= (handshake, STARTTLS, certificate) [DTS errors];
imapflow stamps =tlsFailed: true= on the error and uses code =UPGRADE_TIMEOUT= /
=STARTTLS_INJECTION= for the STARTTLS paths [SRC]. Certificate validation is on by default
in both (=tls.rejectUnauthorized: true=); the library exposes =:tls {:reject-unauthorized ..
:ca .. :min-version .. :servername ..}= as a verbatim passthrough (14.1) and never defaults it
off. Pinning: pass =:ca= (PEM) or =:check-server-identity= (a fn) in that blob — both are Node
=tls.connect= options (13.5 for the smoke host).

** 4.5 IDLE state machine as implemented [SRC commands/idle.js, imap-flow.js autoidle/connectionBusy]
- =idle()= -> =run('IDLE', maxIdleTime)=: if the server has =IDLE=, loops =runIdle= sessions;
  each session sends =IDLE=, waits for the =+= continuation, then sits until =preCheck()= is
  called (by ANY other command entering =run()=, by =close()=, or by the =maxIdleTime= timer)
  which writes =DONE=; the tagged OK ends the session. Without =IDLE= it falls back to a
  polling loop (=NOOP= / =STATUS= / =SELECT= every =min(2 min, maxIdleTime)=).
- Auto-IDLE (=disableAutoIdle: false=): =autoidle()= arms a timer (=autoIdleDelay=) after every
  command *unless the connection is busy*: =connectionBusy()= = a mailbox lock is held or
  queued, a command is in flight or queued, or a download stream is open. So *while
  =getMailboxLock= is held there is NO auto-IDLE and NO push notifications* — the release
  restarts it. Untagged responses still arrive during normal commands, so ='exists'= can also
  fire mid-FETCH.
- Timers (auto-IDLE, IDLE restart, poll) are =unref='d: an idle process is not kept alive by
  them; the library's watcher (10.2) therefore has to hold its own reference if the caller's
  process has nothing else to do (a pending promise / channel take does that).
- The promise returned by =idle()= is the natural "one IDLE session" unit; events flow through
  the emitter concurrently with it.

* 5. IMAP semantics the library models
** 5.1 Mailboxes [DTS ListResponse / MailboxObject / StatusObject][RFC 3501 §7.2.2, RFC 6154]
- =ListResponse=: =path= (unicode), =pathAsListed= (wire, modified-UTF-7 decoded by imapflow),
  =name=, =delimiter= (="."= or ="/"=), =parent: string[]=, =parentPath=, =flags: Set<string>=,
  =specialUse?=, =specialUseSource?: 'user'|'extension'|'name'=, =listed=, =subscribed=,
  =status?= (if =statusQuery=).
- Mailbox attributes (LIST flags): =\HasChildren= / =\HasNoChildren= (RFC 5258), =\Noselect=
  (cannot be SELECTed — skip), =\Noinferiors=, =\Marked= / =\Unmarked=, =\NonExistent=,
  =\Subscribed=, =\Remote=; special-use (RFC 6154 or XLIST): =\All=, =\Archive=, =\Drafts=,
  =\Flagged=, =\Junk=, =\Sent=, =\Trash= (+ imapflow's non-standard =\Inbox= for INBOX and
  =\Important=). imapflow ALSO guesses special-use from localized folder names when the server
  does not advertise SPECIAL-USE (=specialUseSource: 'name'=) [DTS special-use.d.ts].
- =MailboxObject= (after SELECT): =path=, =delimiter=, =flags: Set= (FLAGS), =permanentFlags?:
  Set= (=\*= means any keyword may be created), =uidValidity: bigint=, =uidNext=, =exists=,
  =unseen?= (the FIRST unseen seq number, not a count), =highestModseq?: bigint=, =noModseq?=,
  =mailboxId?= (OBJECTID), =appendlimit?=, =readOnly?=, =specialUse?=.
- =StatusObject= / =StatusQuery=: =messages=, =recent= (always 0 on IMAP4rev2), =uidNext=,
  =uidValidity: bigint=, =unseen= (a COUNT here), =highestModseq: bigint=, =size= (STATUS=SIZE or
  rev2), =deleted= (rev2). Items the server cannot report are omitted.
- Paths: =string | string[]=; arrays are joined with the delimiter and the personal namespace
  prefix is added (e.g. =INBOX.= on Dovecot/Courier layouts). Unicode allowed (UTF8=ACCEPT or
  modified UTF-7 handled by imapflow).
- =UIDVALIDITY=: if it changes, every cached UID is invalid (RFC 3501 §2.3.1.1).

** 5.2 Message flags [RFC 3501 §2.3.2][DTS][SRC tools.js]
System flags: =\Seen=, =\Answered=, =\Flagged=, =\Deleted=, =\Draft=, =\Recent= (read-only,
gone in IMAP4rev2). Keywords (custom flags, no backslash): any atom if =permanentFlags= has
=\*=; common IANA-registered ones =$Forwarded=, =$MDNSent=, =$Junk=, =$NotJunk=, =$Phishing=,
=$Important=; Apple colors =$MailFlagBit0/1/2= (3-bit index into red, orange, yellow, green,
blue, purple, grey — imapflow derives =flagColor= and =setFlagColor= writes them). imapflow
represents flags as =Set<string>= with the backslash; STORE drops flags not allowed by
=permanentFlags= (add/set) silently [SRC store.js canUseFlag]. The library models flags as a
set of strings exactly as on the wire (="\\Seen"=) plus convenience predicates (14.3); it
does not invent keyword-to-keyword translations (=:seen= <-> ="\\Seen"=) beyond the *search*
DSL where imapflow itself uses booleans.

** 5.3 Sequence sets vs UIDs [RFC 3501 §2.3.1][DTS MessageRange / SequenceString][DOC basic-usage]
- Sequence numbers are positional (1..N) and shift on EXPUNGE; UIDs are stable within a
  UIDVALIDITY. Every imapflow range method takes ={uid: true}= to interpret the range as UIDs;
  results always carry both =seq= and =uid=.
- =MessageRange= = =SequenceString= (string / number / bigint: ="1:10"=, ="1,3,5"=, ="100:*"=,
  ="*"=; imapflow extension ="*:-10"= = last 10) | =number[]= | =SearchObject= (resolved by a
  SEARCH first).
- House position: the library is *UID-first*: every public fn takes and returns UIDs and
  passes ={uid: true}=; sequence numbers are exposed read-only as =:seq= on fetched messages
  and on expunge events when the server did not give a UID (14.3).

** 5.4 Search DSL (=SearchObject=) [DTS types.d.ts][SRC search-compiler.js][PROBE]
Keys and the IMAP keys they compile to (all ANDed at one level):
| Key (imapflow)                       | IMAP                                   | Notes |
|--------------------------------------+----------------------------------------+-------|
| =seq= / =uid= (SequenceString)       | bare sequence-set / =UID <set>=        | |

| =sentBefore= / =sentOn= / =sentSince= | =SENTBEFORE= … (Date: header)          | day granularity |
| =keyword= / =unKeyword= (string)     | =KEYWORD $X= / =UNKEYWORD $X=          | |

| =modseq= (bigint/number)             | =MODSEQ n=                             | needs CONDSTORE |
| =emailId= / =threadId=               | =EMAILID= / =THREADID= (OBJECTID) or X-GM-MSGID/THRID | |
| =not= (SearchObject)                 | =NOT (…)=                              | |

| =gmraw= / =gmailraw= / =labels {has, not}= | =X-GM-RAW=                        | Gmail only |
Empty query -> =[]= attributes -> imapflow sends =ALL= (the compiler returns [] and the SEARCH
command supplies the default) — 13.6. Options: ={uid: true}= (return UIDs), =returnOptions:
['MIN'|'MAX'|'COUNT'|'ALL'|{partial: '1:100'}]= -> =ESearchResult {count?, min?, max?, all?:
"1,5:10", partial?: {range, messages}, modseq?}= (imapflow emulates when the server lacks
ESEARCH).
Date/timezone: IMAP dates carry no time; the server compares against its own notion of the
message's date in *its* timezone. *Corrected in phase 3 [SRC tools.js formatDate /
toValidDate, search-compiler.js processDateField, verified offline against the installed
2.0.6]:* imapflow renders every date value from its *UTC* ISO components
(=toISOString().substr(0, 10)=), NOT local components as this section first claimed — but
it first runs EVERY value, strings included, through =new Date(value)=, so a string is not
passed verbatim: ="24-Sep-2026"= is parsed as LOCAL midnight and comes out as
=23-Sep-2026= on a UTC+3 machine, while ="2026-09-24"= (date-only ISO) is parsed as UTC
midnight and survives. =BEFORE= / =SENTBEFORE= with a non-midnight time are shifted +24 h.
Invalid strings compile to nothing (silently). House rule (12.4 / 13.7): =imap/search-date=
normalises ="YYYY-MM-DD"=, ="DD-Mon-YYYY"=, =#inst= (UTC calendar day) and ={:year :month
:day}= to the date-only ISO form and rejects anything else with =:argument-error
:bad-search-date= before imapflow sees it.

** 5.6 Body structure tree (=MessageStructureObject=) [DTS][RFC 3501 §7.4.2]
={part?: "1.2", type: "text/plain" (full type/subtype, lower-case), parameters?: {charset, name,
boundary…}, id?: "<cid>", encoding?: "base64"|"quoted-printable"|"7bit"|"8bit"|"binary",
size?, envelope? (message/rfc822 parts), disposition?: "attachment"|"inline",
dispositionParameters?: {filename…}, childNodes?: [...], md5?, language?: string[], location?,
description?, lineCount?}=. Multipart nodes have =type: "multipart/mixed"= etc. and
=childNodes=; part numbers: children of the root multipart are =1=, =2=…; nested =1.1=, =1.2=;
a non-multipart root is part =1= (=part= undefined on the root). This matches the =partId=
mailparser assigns (=1.2.2= for the inline image of the probe message in 7.2) [PROBE].
Attachment detection heuristic (imapflow docs): =disposition === 'attachment'= or a non-text,
non-multipart type without disposition; inline images live under =multipart/related= with an
=id= (cid). Section 9.3 uses this tree to download single parts without fetching =source=.

** 5.7 Expunge semantics [RFC 3501 §6.4.3, RFC 4315, RFC 7162][DTS]
- Deleting = STORE =\Deleted= + =EXPUNGE= (all =\Deleted= in the mailbox!) or =UID EXPUNGE
  <set>= (UIDPLUS; only those). imapflow's =messageDelete= uses UID EXPUNGE when capable
  (safe) — the library's =delete!= therefore never expunges *other* clients' =\Deleted= marks
  unless UIDPLUS is missing (13.11). =mailboxClose()= sends CLOSE which expunges everything
  =\Deleted= in a read-write mailbox (12.7); =UNSELECT= is what a non-expunging close needs and
  imapflow does not expose it — the library opens read-only when the caller only reads.
- Notifications: one ='expunge'= event per message, =seq= (shifting!) unless QRESYNC gives
  =uid= (VANISHED, =vanished: true=; =earlier: true= for VANISHED (EARLIER) replays on SELECT).
  Applying seq-based expunges to a cached list requires processing them in order and
  decrementing later seqs — the reason the library enables =qresync= (10.3) and reports UIDs.
- =\Recent=: unreliable / gone in rev2; never relied on.

** 5.8 QUOTA, CONDSTORE / MODSEQ, other extensions [DTS][RFC 2087/9208, 7162]
- QUOTA: =getQuota(path) -> {path, storage?: {used, limit} (bytes; the wire unit is KiB — imapflow
  converts, 13.12), messages?: {used, limit}, ...other resources} | false=.
- CONDSTORE: auto-enabled when advertised (=enabled= has =CONDSTORE=); then =mailbox.highestModseq=,
  =message.modseq= (bigint) on every fetch, =fetch(..., {changedSince})=, =search({modseq})=,
  store =unchangedSince=, =status({highestModseq})=, ='flags'= events carry =modseq=. QRESYNC
  (opt-in =qresync: true=) additionally: VANISHED expunges with UIDs. Yes, imapflow surfaces
  MODSEQ fully; the library exposes it as =:modseq= (a string, 14.2) and =changed-since=.
- BINARY (RFC 3516): =fetch(..., {binary: true})= makes the server decode the CTE (=binaryParts=
  says which parts arrived decoded); =download()= decodes client-side anyway.
- COMPRESS=DEFLATE, ID, ENABLE, UTF8=ACCEPT, MOVE, UIDPLUS, LIST-STATUS, LIST-EXTENDED,
  SPECIAL-USE, OBJECTID, STATUS=SIZE, APPENDLIMIT, NAMESPACE, IMAP4rev2: all detected and used
  automatically; the library surfaces =capabilities= and otherwise stays extension-agnostic.
- Not exposed by imapflow (so not by the library): NOTIFY (RFC 5465), SORT/THREAD (RFC 5256),
  MULTIAPPEND, UNSELECT, ACL, METADATA. Server-side sort/thread is therefore =none= (13.13).

** 6.3 Headers Map value rules [SRC processHeaders][PROBE]
- Every header value is RFC 2047-decoded and trimmed; repeated headers become arrays (=x-lower
  -> ['a','b']=), except the "single" keys (=message-id=, =content-id=, =from=, =sender=,
  =in-reply-to=, =reply-to=, =subject=, =date=, =content-disposition=, =content-type=,
  =content-transfer-encoding=, =priority=, =mime-version=, =content-description=, =precedence=,
  =errors-to=, =disposition-notification-to=) which keep the LAST occurrence.
- Structured: =content-type= / =content-disposition= / =dkim-signature= ->
  ={value: "multipart/mixed", params: {boundary: "…", charset, name, filename}}=.
- Addresses (=from to cc bcc sender reply-to delivered-to return-path
  disposition-notification-to=) -> ={value, html, text}= as in 6.1; IDN domains decoded to
  Unicode; RFC 2047 words inside addr-spec are rejected (address blanked) — security fix.
- =date= -> =Date= (invalid -> now); =references= -> array; =message-id= / =in-reply-to= ->
  bracket-normalised; priority family -> ='priority'=; =list-*= -> ='list'= object.
- Everything else -> string (or array).

** 6.4 =MailParser= stream class [SRC mail-parser.js][DOC]
Transform stream (object mode readable). Events: ='headers'= (Map), ='headerLines'=, ='data'=
objects: ={type: 'attachment', content: Readable, release(), filename, contentType, partId,
contentDisposition, contentId, cid, related, headers}= (checksum/size only after the content
stream ends) — *parsing pauses until =release()= is called* (back-pressure); then one
={type: 'text', text, html, textAsHtml}= at the end; ='end'=; ='error'= (also emitted for "HTML
too long" and "Failed to parse HTML", after which text gets a placeholder). Order observed

library exposes as a channel in phase 4 (9.4).

** 6.5 Options (both APIs) [DOC][SRC]
=skipHtmlToText=, =maxHtmlLengthToParse= (default Infinity; exceeding -> 'error' event ->

* 7. MIME / message model
** 7.1 Content types, transfer encodings, charsets [RFC 2045/2046/2047][DTS mime-node][PROBE]
- Text parts: =text/plain; charset=utf-8= and =text/html; charset=utf-8=. nodemailer picks the
  Content-Transfer-Encoding automatically: =7bit= for ASCII with lines <= 76 chars,
  =quoted-printable= for mostly-ASCII text, =base64= otherwise (=textEncoding= tilts the
  choice, =encoding= forces it). Attachments default to =base64= (=8bit= for =message/*=);
  =contentTransferEncoding: false= lets nodemailer choose. [DOC message, attachments][PROBE:
  ünïcode text -> quoted-printable, html without non-ASCII -> 7bit, png -> base64]
- Header encoding: non-ASCII header values (Subject, display names, filenames) become RFC
  2047 encoded-words (=?UTF-8?Q?…?= or =?UTF-8?B?…?=); filenames additionally via RFC 2231
  when needed. mailparser decodes all of them; imapflow decodes ENVELOPE subject/names and
  BODYSTRUCTURE params.
- Charsets on the way in: mailparser converts every text part to UTF-8 via iconv-lite
  (6.5); imapflow =download()= converts text parts to UTF-8 too (=meta.charset= reports the
  original); raw =source= / =bodyParts= are untouched bytes.
- Line endings: RFC 5322 requires CRLF on the wire; nodemailer's SMTP transport normalises
  bare LF to CRLF while transmitting; the stream transport keeps what it generated
  (=newline= option); mailparser normalises text bodies to =\n=.

** 7.2 Multipart tree nodemailer builds (=MailComposer.compile=) [SRC mail-composer compile][PROBE]
| Content present                                   | Root                                                        |
|---------------------------------------------------+-------------------------------------------------------------|
| text only / html only / one attachment only       | that single part                                            |
| text + html                                       | =multipart/alternative= [text, html]                        |
| html + cid attachments                            | =multipart/related; type="text/html"= [html, related…]      |
| text + html + cid attachments                     | =multipart/alternative= [text, =multipart/related= [html, related…]] |
| anything + regular attachments (>1, or >=1 with a body) | =multipart/mixed= [ (alternative | related | single body), attached… ] |
| =raw=                                             | =message/rfc822= node emitting the raw bytes verbatim       |
Alternative order is fixed: text, watchHtml, amp, html, icalEvent, then =alternatives[]=.
Probe (text + html + 1 cid image + 2 attachments) produced exactly
=mixed[ alternative[ text/plain(qp), related[ text/html(7bit), image/png(inline, cid) ] ],
text/plain(attachment), application/octet-stream(attachment) ]= with parts numbered by
mailparser as =1.2.2=, =2=, =3=.

** 7.3 Inline vs attachment disposition and Content-ID [RFC 2183, RFC 2392][DOC attachments, embedded-images]
- =contentDisposition= defaults to =attachment=; it is =inline= for =message/*= parts and for
  *image* attachments that carry a =cid= (so an image with a cid but no html body still goes
  out as an inline attachment under =multipart/mixed=, and a non-image with a cid stays
  =attachment= but is still moved into =multipart/related= if there is html).
- =cid= -> =Content-ID: <cid>= header; html references it as =src="cid:<cid>"=; the related
  container is only built when the message has an =html= body.
- On parse, mailparser gives =cid= (bare) + =contentId= (bracketed) + =related= (ancestor is
  multipart/related) and rewrites =cid:= URLs in =html= to =data:<type>;base64,…= unless told
  not to. The library defaults to KEEPING cid links (=keepCidLinks: true=) and exposing the
  =cid= on the attachment map, so the caller decides (12.8 explains the memory reason).

** 7.4 Address and date formats [RFC 5322 §3.3/§3.4][PROBE]
- Address wire forms: =addr-spec= (=a@b.c=), =name-addr= (=Name <a@b.c>=, quoted-string names
  ="Doe, John" <a@b.c>=), groups (=Team: a@b, c@d;=), obsolete forms. nodemailer renders
  ={name, address}= with quoting/encoding as needed (="Doe, John" <john@example.com>= and
  ==?UTF-8?B?QsOp?= <b@example.com>= in the probe). addressparser handles quoted commas,
  groups, and tries to recombine unquoted =Doe, John <a@b>= (heuristic; 12.1). RFC 2047 in
  a display name is NOT decoded by addressparser itself (probe: name stayed
  ==?UTF-8?Q?J=C3=BCrgen?==); mailparser decodes it in =decodeAddresses=.
- Dates: wire =Date: Thu, 24 Sep 2026 23:08:56 +0000= (RFC 5322 date-time; nodemailer writes
  UTC). mailparser -> JS =Date= (invalid -> now); imapflow ENVELOPE =date= -> =Date= (invalid ->
  raw string); =internalDate= (server receipt time, the value SEARCH SINCE/BEFORE use) ->
  =Date=. The library renders every date as an ISO-8601 UTC string (14.2) and keeps
  =:internal-date= separate from the header =:date= (12.4).

** 7.5 What mailparser resolves automatically vs what stays raw
Resolved: RFC 2047 words, charsets to UTF-8, transfer encodings (attachment =content= is
decoded bytes), format=flowed text (=FlowedDecoder=), quoted-printable soft breaks, IDN
domains, message-id normalisation, priority normalisation, nested rfc822 flattening, cid
-> data URI. Raw: =headerLines= (exact lines), attachment =headers= Map (parsed like the
top-level), unknown charsets (bytes as-is), DKIM signature (parsed to value/params only,
not verified), no HTML sanitising (caller's job — the docs warn about XSS).

* 9. Attachment handling under the no-interop rule

| =:content "SGVsbG8=" :encoding :base64=               | =content: "SGVsbG8=", encoding: "base64"= (nodemailer decodes) |
| =:bytes <byte-array or Uint8Array-like opaque>=       | =content: Buffer.from(bytes)= — only the binding touches Buffer |
| =:path "/abs/file.pdf"=                               | =path= — *refused by default* (=disableFileAccess=) unless the client is built with =:allow-file-access? true= (11.4) |
| =:href "https://…"=                                   | =href= — refused by default (=disableUrlAccess=)    |
| =:stream <opaque stream handle from attachment/stream…>= | =content: <Readable>= (handle created by the binding, so no interop at the call site) |
| =:filename :content-type :content-disposition :cid :content-transfer-encoding :headers= | camelised 1:1 |
Base64 strings are the primary no-interop representation for binary content: they are plain
CLJS strings, serialise to EDN/JSON, and nodemailer decodes them itself. Byte arrays
(=js/Uint8Array= is what =(byte-array …)= is NOT in CLJS — CLJS has no =byte-array=; a
=js/Uint8Array= or a vector of ints) are accepted as an opaque =Bytes= wrapper created by
=email-cljs.attachment/bytes= (14.4) so callers who already hold binary data need no interop.

** 9.3 Reading: three sources of attachment bytes
| Source                               | Shape from the package                                  | Library exposure |
|--------------------------------------+---------------------------------------------------------+------------------|
| mailparser =simpleParser=            | =content: Buffer= (decoded), =size=, =checksum=          | =:content= = opaque =Bytes= wrapper (prints as =#email-cljs/bytes {:size N}=) + =:content-base64= on demand via =attachment/->base64= (not eagerly: memory) + =attachment/->string= (charset aware) + =attachment/write-file!= |
| imapflow =download(uid, part)=       | ={meta {contentType charset disposition filename encoding expectedSize flowed delSp}, content: Readable}= decoded | =imap/download!= -> promise of the same attachment map with =:content Bytes= (binding drains the stream), plus =imap/download-chan= (core.async channel of byte chunks as =Bytes=) for large parts; =:max-bytes= honoured |
| imapflow =fetch {bodyParts}= / =source= | =Map<string, Buffer>= raw (transfer-encoded unless BINARY) / =Buffer= | =:source= as =Bytes=; the library does not expose =bodyParts= raw (use =download!= which decodes) except =:headers=, which the binding parses into the 6.3 header map by running mailparser over the header block |
Why an opaque wrapper and not always base64: a base64 string of a 25 MB attachment is 33 MB
of JS string plus the Buffer — doubling memory per attachment; the wrapper keeps ONE Buffer
and converts lazily. Both representations exist (=Bytes= in, base64 out on request), per the
brief's "both?" question: *yes, both, with =Bytes= as the carrier and base64 as the
serialisable view*.

** 9.4 Size limits and streaming
- SMTP: server =SIZE= extension (in =info.ehlo=); nodemailer refuses up-front with EMESSAGE
  "Message size larger than allowed" when it can compute the size; otherwise the 552 at DATA
  surfaces as EMESSAGE. Attachments of any size stream from =path=/=Readable= without
  buffering; base64 strings and =Bytes= are in memory.
- IMAP: =APPENDLIMIT= (capability / =mailbox.appendlimit=) for =append!=; =maxLiteralSize=
  (default 1 GB) bounds what a FETCH may push into memory — the library defaults it to
  256 MB (13.14) and uses =download()= (chunked =chunkSize= 64 KB, =maxBytes=) rather than
  =source= for big messages.
- mailparser: streaming =MailParser= keeps attachments as streams with back-pressure
  (=release()=); simpleParser buffers everything. Phase 4 exposes =message/parse-chan= (a
  core.async channel of ={:event :headers|:attachment|:text|:end|:error}= where each
  attachment carries its own chunk channel) for the streaming path, and =message/parse!=
  (simpleParser) for the common case.

* 10. IDLE -> core.async design
** 10.1 Constraints from imapflow [DTS][SRC 4.5][DOC]
1. One connection = one command at a time. =idle()= occupies the connection until broken; any
   other command on the same connection breaks it (sends DONE) transparently (=preCheck=),
   runs, and auto-IDLE (if enabled) re-arms 15 s later — but only when no lock is held.
2. Events (='exists'=, ='expunge'=, ='flags'=) are emitted on the client whenever the
   untagged responses arrive, inside or outside IDLE. ='exists'= is the only "new mail"
   signal: it carries the new =count= and =prevCount=, NOT the message. Fetching the new
   messages is a separate command (=UID SEARCH UID <uidNext-before>:*= or =FETCH <prevCount+1>:*=).
3. =idle()= resolves when the session ends (DONE acknowledged, server-terminated, or close);
   with =maxIdleTime= imapflow restarts internally so one =idle()= call can span many sessions.
4. No auto-reconnect: ='close'= means the watcher is over; ='error'= usually precedes it.
5. Holding =getMailboxLock= disables auto-IDLE; calling =idle()= manually while holding the
   lock works (the lock only gates auto-IDLE via =connectionBusy=; a manual =idle()= is a
   command like any other) — 13.15 verifies this live because it is the crux of the design.

** 10.2 House design: =imap/watch!= returns a channel
#+begin_src clojure
(imap/watch! conn "INBOX" {:buffer 64 :fetch? true :query {:envelope true :flags true}})
;; => core.async channel; events (kebab maps):
{:event :open     :path "INBOX" :mailbox {:path "INBOX" :exists 42 :uid-next 1001 :uid-validity "17…"}}
{:event :new-mail :path "INBOX" :count 43 :prev-count 42}           ; every EXISTS whose count changed (was ":exists")
{:event :new-mail :path "INBOX" :count 43 :prev-count 42 :uids [1001] :messages [{:uid 1001 :seq 43 :envelope {...} :flags #{"\\Seen"}}]} ; with :fetch? true, only when count > prev-count
{:event :expunge  :path "INBOX" :uid 998 :seq nil :vanished true}    ; seq-only when the server has no QRESYNC
{:event :flags    :path "INBOX" :uid 1000 :seq 42 :flags #{"\\Seen" "\\Flagged"} :modseq "5"}
{:event :idle-restart :path "INBOX"}                                 ; each :max-idle-ms cycle (29 min default)
{:event :error    :error <ex-info :email-cljs/imap-error|:network-error>}
{:event :closed   :path "INBOX" :reason :stopped|:consumer-closed|:connection-lost|:error} ; last event; channel closed right after
#+end_src
As built in phase 3 (=email-cljs.imap/watch!= + =stop-watch!= + =watching?=): the ':exists'
and ':new-mail' rows above were merged into ONE =:new-mail= event per EXISTS (the brief's
event list), and ':close' became =:closed= with a keyword reason. The IDLE restart is driven
by the library, not by imapflow's =maxIdleTime= (which loops *inside* one =idle()= call and
would make the restart invisible): =maxIdleTime= is passed as =false=, an unref'd timer
breaks IDLE with a =noop()= every =:max-idle-ms=, =idle()= resolves, the loop emits
=:idle-restart= and re-enters =idle()= — verified with a fake connection and a 30 ms period.
Mechanics (all inside =email-cljs.imap-binding=):
- The watcher owns a *dedicated* =ImapFlow= connection (=:connection= option may pass one, but
  the default is to open a second connection from the same client config): a connection in
  IDLE cannot serve the caller's fetches without DONE/IDLE churn, and a fetch inside the
  watcher's own event handling would deadlock if the caller is mid-=fetch= on that
  connection. Cost: one extra TLS session per watched mailbox; benefit: no cross-talk.
- =disableAutoIdle: true= on every connection the library opens (10.1 point 1: explicit
  control), =qresync: true= (UID expunges), =maxIdleTime= 29 min default (13.10).
- Loop: =connect= -> =mailboxOpen(path, {readOnly: true})= -> put =:open= -> =loop= (=idle()=
  -> when it resolves and the connection is usable, put =:idle-restart=, repeat). Listeners on
  ='exists'= / ='expunge'= / ='flags'= translate payloads and =put!= them; on ='exists'= with
  =:fetch? true= the loop breaks IDLE by running =fetchAll("<prevCount+1>:*", query)= (a
  command on the watcher's own connection — allowed because the watcher is not iterating a
  =fetch= generator) and puts =:new-mail=; then =idle()= again.
- Back-pressure: =put!= with a dropping/sliding buffer chosen by the caller (=:buffer= n
  -> =(async/chan (async/sliding-buffer n))= default; =:buffer :block= uses an unbuffered
  channel and =>!= inside a =go= so a slow consumer pauses the loop — untagged events are
  still received and applied by imapflow, only the *forwarding* pauses).
- Stop: =imap/stop-watch!= (or closing the channel from the consumer side: the loop checks
  =(async/put! …)= returning false) -> =logout()= (or =close()= after a timeout), then the
  channel is closed. Process liveness: the pending =idle()= promise + the open socket keep
  Node alive; imapflow's own timers are unref'd, which is fine.
- Errors: ='error'= -> =:error= event; ='close'= -> =:close= event -> channel closed. The
  watcher never reconnects (house rule: the caller decides; a =imap/watch-forever!= helper
  with backoff is a phase-3 candidate, 13.16).

** 10.3 Why QRESYNC and why not =expungeHandler=
=expungeHandler= replaces the event (it is for servers that need the client to *acknowledge*
each expunge before the next command); the event form is enough for a channel. QRESYNC turns
seq-only expunges into UID expunges (=vanished: true, uid=), which is what a UID-first API
needs; when the server lacks QRESYNC the event carries only =seq= and the library reports
=:uid nil= with =:seq= — consumers keeping a seq->uid map must apply them in order (12.7).

* 11. Message building: nodemailer model vs raw
** 11.1 =message/build= input (kebab, phase 2) -> =SendMailOptions= [2.4]
#+begin_src clojure
{:from {:name "Doe, John" :address "john@example.com"}     ; or "john@example.com" or "Doe <j@x>"
 :to ["a@example.com" {:name "Bé" :address "b@example.com"}]
 :cc "c@example.com" :bcc ["hidden@example.com"] :reply-to "…" :sender "…"

 :attachments [{:filename "a.txt" :content "hello" :content-type "text/plain"}
               {:filename "logo.png" :content "iVBORw0KGgo=" :encoding :base64 :cid "logo@x"}
               {:filename "big.bin" :bytes (attachment/bytes …)}]

Translation rules (14.1): keys camelised; keyword enum values rendered as strings (=:high= ->
="high"=, =:base64= -> ="base64"=); =:headers= passed verbatim (user-owned, string keys kept);
address maps camelised (=:name= =:address= are single words anyway); =:date= inst -> =Date=
(binding); =:attachments= translated element-wise with the 9.2 rules.

** 11.2 Output of =message/build= (no transport): a map of bytes + metadata
=(message/build msg)= -> promise of ={:source <Bytes> :message-id "<…>" :envelope {:from :to}
:size N}= via =MailComposer.compile().build()= + =getEnvelope()= + =messageId()= — used for
=imap/append!= (drafts, Sent copies: SMTP does not store a copy in Sent — 12.12) and tests.
=(message/build-string msg)= -> promise of the RFC 822 string (=newline :unix= for tests).

** 11.3 Raw messages
=:raw= (string / =Bytes=) sends verbatim; =:envelope= is then mandatory (=:argument-error=
before any network call, since nodemailer would only fail at =API= time). Per-attachment
=:raw= (pre-built MIME node) and per-alternative =:raw= are passed through; documented as
"you own the headers".

** 11.4 Security defaults the library enforces
=disableFileAccess: true= and =disableUrlAccess: true= on every transport AND message unless
the client is created with =:allow-file-access? true= / =:allow-url-access? true=; a message
using =:path= / =:href= is rejected with =:argument-error :reason :file-access-disabled= before
the send (nodemailer would return EFILEACCESS/EURLACCESS). Reason: message maps often come
from JSON; =path= would read any file the process can read.

* 12. Pitfalls
1. *Commas in display names.* ='Doe, John <a@b>'= unquoted splits into a bogus "Doe" entry
   unless nodemailer's heuristic recombines it (it does only when an angle-bracket address
   follows). Always emit ={:name :address}= maps from the library and quote when rendering
   (=addressparser= round-trips ="Doe, John" <a@b>= correctly [PROBE]). Parsing user-supplied
   strings: expose =message/parse-addresses= (addressparser) and document the quoting rule.
2. *RFC 2047 in names.* addressparser leaves encoded-words in =name= (probe: ==?UTF-8?Q?J=C3=BCrgen?==);
   only mailparser decodes them. The library's parse path goes through mailparser (or
   =libmime.decodeWords= in the binding) so callers never see encoded-words.
3. *Charsets beyond UTF-8.* mailparser decodes via iconv-lite (hundreds of charsets, incl.
   windows-125x, ISO-8859-x, KOI8, GBK, Shift_JIS, EUC-KR); JIS family via encoding-japanese;
   the =EUC-JP= label (hyphenated) falls to iconv-lite (fine, iconv-lite supports it); unknown
   labels pass bytes through undecoded. Search strings with non-ASCII need UTF-8 CHARSET
   support on the server (imapflow sends CHARSET UTF-8 when needed; Dovecot ok — 13.17).
4. *Search dates and time zones.* SINCE/BEFORE/ON are date-only, compared against
   INTERNALDATE in the server's zone; SENTSINCE against the =Date:= header. imapflow 2.0.6
   re-parses every date value (strings too) with =new Date()= and renders it from UTC ISO
   components (5.4, corrected in phase 3) — so "pass strings verbatim" is NOT possible: a
   wire-spelled ="DD-Mon-YYYY"= string shifts a day east of UTC. House rule (as built):
   =imap/search-date= accepts an =#inst= (its UTC calendar day), ="YYYY-MM-DD"=,
   ="DD-Mon-YYYY"= or ={:year :month :day}=, always hands imapflow the date-only ISO form
   (which =new Date()= reads as UTC midnight and =formatDate= renders back unchanged, and
   which keeps BEFORE off the +24 h path), and rejects anything else — 13.7.
5. *Envelope =Date= vs =internalDate=.* The header date is whatever the sender wrote (can be
   absent, wrong, in any zone; mailparser silently substitutes NOW for unparseable ones —
   the library detects that by re-reading =headerLines= and reports =:date nil=). =internalDate=
   is the server's receipt time and is what SEARCH SINCE uses; "newest" ordering must use UID
   or =internalDate=, not the header.
6. *Huge attachments / memory.* =simpleParser= and =fetch {source: true}= buffer everything;
   =maxLiteralSize= caps a single literal at 1 GB by default — the library lowers it (13.14)
   and prefers =bodyStructure= + =download()= per part. Data-URI conversion in mailparser
   (=cid:= -> =data:=) creates a second base64 copy of every inline image inside =html= — the
   library keeps cid links by default (7.3).
7. *Expunge and sequence numbers.* CLOSE expunges; seq numbers shift with every EXPUNGE; a
   cached ={seq -> uid}= map must be updated in event order. UID-first API + QRESYNC + read-only
   opens for readers avoid most of it; =delete!= uses UID EXPUNGE (UIDPLUS) — on a server
   without UIDPLUS it falls back to EXPUNGE, which also purges other =\Deleted= marks (13.11).
8. *Inline image detection.* "Attachment" vs "inline" is a disposition, =related= tells
   whether the part sits under multipart/related, and =cid= tells whether html can reference
   it; all three are independent. The library exposes all three and a derived =:inline?=
   (= disposition inline AND cid AND related).
9. *EventEmitter 'error'.* An imapflow client with no ='error'= listener throws on emit and
   crashes the process; the binding attaches one at construction, always.
10. *imapflow logs to stdout by default* (pino JSON). The library passes =logger: false=
    unless =:logger= (a map of fns) or =:log-chan= (core.async, via =emitLogs=) is given.
11. *Credentials in errors/logs.* imapflow masks credential frames in =logRaw=; nodemailer's
    =debug= logs the AUTH exchange base64 — the library never enables =debug=/=transactionLog=
    from a boolean; only an explicit =:debug-logger= fn receives them, and =:executed-command=
    is dropped from =:auth-error= data.
12. *Sent folder.* SMTP delivery does not store a copy in =Sent=; clients do that with IMAP
    APPEND. Phase 3 offers =(imap/append! conn "Sent" built-message #{"\\Seen"})= and phase 2's
    =send!= accepts =:save-to-sent {:imap conn :mailbox "Sent"}= (13.18 for the smoke: does
    the host auto-save? Dovecot does not; a Sieve/postfix setup might).
13. *Send -> IMAP visibility latency.* Local delivery on the same box (postfix -> dovecot LMTP)
    is typically sub-second but not synchronous with the SMTP 250; the smoke must poll
    (=search {:header {"Message-ID" id}}= every 500 ms up to 30 s) or use the watcher — 13.1.
14. *Pool vs single connection.* A pooled transport keeps sockets open until =socketTimeout=
    (10 min) or =close()=; a process that forgets =close!= keeps Node alive. Single-connection
    mode (default) opens/closes per message: simpler, slower, no lingering sockets. The
    library defaults to single and exposes =:pool {:max-connections 5 :max-messages 100
    :rate-limit n :rate-delta ms}= as an option (13.9).
15. *Partial recipient rejection resolves, not rejects* (2.5): a =send!= caller must inspect
    =:rejected=; the library adds =:all-accepted?= to the result and a =:strict? true= send
    option that rejects with =:smtp-error= when =:rejected= is non-empty (after the message was
    still delivered to the accepted ones — there is no way to undo).
16. *=fetch()= generator deadlock.* No IMAP command may run while iterating =fetch()=; the
    binding always drains with =fetchAll= (bounded ranges, the caller paginates with
    =:uid-range= / =:limit=) or the async generator into a channel that the caller reads
    *after* the generator finished — never a callback-per-message API that could issue
    commands.
17. *Flags dropped silently.* Adding a keyword the mailbox's =permanentFlags= does not allow
    is a silent no-op in imapflow; the library checks =permanent-flags= (after open) and
    rejects with =:argument-error :reason :flag-not-permitted= when neither the flag nor =\*=
    is allowed.
18. *bigint everywhere.* =uidValidity=, =highestModseq=, =modseq=, =changedSince=,
    =unchangedSince= are BigInt; =js->clj= leaves them as BigInt objects which print oddly and
    do not compare with =. The binding renders them as decimal strings and parses strings
    back (14.2).
19. *Maps and Sets.* imapflow returns =Set= (flags, labels, mailbox flags), =Map= (bodyParts,
    uidMap, capabilities), mailparser returns =Map= (headers); =js->clj= does NOT convert them
    (they become opaque). Every binding walks them explicitly (14.2).

* 17. Phase 2+3 implementation notes and inventory corrections (2026-09-25)
Found while implementing against the installed packages (all offline; every item is covered
by a test in =test/email_cljs/{smtp,imap,attachment}_test.cljs=):
1. *Search dates (5.4 / 12.4 / 13.7 corrected).* imapflow 2.0.6 renders dates from UTC ISO
   components, not local ones, AND re-parses string values with =new Date()=: the settled
   "date strings pass verbatim" cannot hold (a ="DD-Mon-YYYY"= string is read as local
   midnight and comes out a day early on this UTC+3 machine). As built: every date form is
   normalised to ="YYYY-MM-DD"= (=imap/search-date=), which imapflow reads as UTC midnight and
   renders back unchanged; unknown spellings are rejected before the connection is touched.
   =#inst= -> UTC calendar day stands.
2. *HEADER names upper-cased on the wire* — confirmed offline (=HEADER MESSAGE-ID "<..>"=);
   keyword header names in the DSL are rendered =X-Foo= style before that.
3. *Bare EXPUNGE / UID EXPUNGE.* imapflow exposes no method for them (=messageDelete= always
   adds =\\Deleted= first; =mailboxClose= sends CLOSE). The binding runs them through the
   client's =exec(command, attributes)= (public on the JS object, undeclared in the =.d.ts=);
   =uid-expunge!= sends ={type: "SEQUENCE"}= attributes exactly as =commands/expunge.js= does.
   4.3 table: add =exec= (scope: binding-internal).
4. *=maxIdleTime= loops inside one =idle()= call* (=commands/idle.js=; 4.5 was right), so an
   imapflow-driven restart is invisible to the caller. The watcher passes =maxIdleTime: false=
   and restarts itself (NOOP breaks IDLE; =idle()= resolves; =:idle-restart= emitted; IDLE
   re-entered). =idle()= also short-circuits (returns undefined) when =idling= is already true.
5. *nodemailer =normalize()= keeps string =content= as-is* (only Buffers are base64'd and get
   =encoding: "base64"=), so a Bytes attachment reaches the transport as
   ={content: "<base64>", encoding: "base64"}= while a string stays a string. 2.6's description
   of the json transport output is consistent with this.
6. *=Mail.verify()= / =close()= on a plugin transport* simply forward to the plugin (returning
   =false= with a logger warning when the plugin lacks the method); the library's
   =verify-smtp!= therefore resolves =true= for transports without =verify= (json / stream).

* 18. Phase 4+5 implementation notes and live corrections (2026-09-25)
Found while implementing =message= / the mailparser binding (offline, covered by
=test/email_cljs/message_test.cljs=) and while running the live smoke
(=dev/email_cljs/smoke.cljs=, 9/9 sections green against =box.borret.ro=, Dovecot behind
Postfix; three sends per run, all cleaned up). Items marked *LIVE* were observed on the
server and are not predicted anywhere above.
1. *LIVE — WITHIN changes what =:since= / =:before= send.* The server advertises =WITHIN= (RFC
   5032; the 13.2 capability row never listed it) and imapflow 2.0.6's =searchCompiler=
   then renders =:since= / =:before= as =YOUNGER n= / =OLDER n= — the seconds between now and
   the date's UTC midnight (=search-compiler.js= 316-332) — instead of =SINCE= / =BEFORE=
   =<day>=. Consequences: (a) the 13.7 "server-side day comparison" question is moot on
   such servers: the boundary is exactly the UTC midnight the library normalises to
   (17.1 stands, and is now timezone-proof); (b) a day after today's UTC day yields an
   interval of 0 and Dovecot answers =BAD Error in IMAP command UID SEARCH: Invalid search
   interval parameter=; (c) =:on= and the =:sent-*= keys are untouched (calendar days).
   Position as built: =imap/adjust-search-for-within= (pure) runs inside =search!= when
   the connection has WITHIN — =:since <future day>= resolves to no hits without a round
   trip, =:before <future day>= is dropped (always true; ={:all true}= if nothing remains);
   nested =:or= / =:not= dates are left alone and surface as 18.2's =:search-failed=. The
   library does NOT strip =WITHIN= from the capability map (it is imapflow's data).
2. *LIVE — imapflow swallows a refused SEARCH.* =commands/search.js= catches the =NO= / =BAD=,
   logs it at =warn= level and returns =false=, indistinguishable from "no mailbox
   selected" (4.6 / 8.2 list no such case). Position as built: =imap-binding/make-client=
   installs a *capturing logger* (imapflow accepts any object with the level methods;
   only the =err= fields go through =error->map=, never the raw entry) unless =:logger?
   true= asked for the console logger; entries land in =imap/last-warning= (state
   =:last-warning=, distinct from =:last-error=) and =search!= rejects with =:imap-error
   :reason :search-failed {:response-status :response-text :query :path}= when a mailbox
   is open, =:no-mailbox= otherwise. The watcher's connection gets its own capturing
   logger (entries are kept on the control atom, never emitted as =:error= events).
3. *MailComposer drops =Bcc:= by default* (11.2 / 13.20 said only the SMTP transport
   strips it). =MimeNode= skips =Bcc= unless =keepBcc= is set — a property of the compiled
   node (the stream transport sets =mail.message.keepBcc = true= after =compile()=), not a
   composer option. =message/build= therefore strips =Bcc:= like a real send would and
   offers =:keep-bcc? true= (=smtp-binding/compose= sets the property after compile); the
   Bcc recipients are always in the built =:envelope :to=. Live: the delivered message
   carried no =Bcc= header (13.20 confirmed for the SMTP path).
4. *Priority: two corrections.* (a) =X-Priority= / =X-MSMail-Priority= / =Importance= are
   written by nodemailer's *mailer* (=MailMessage.setPriorityHeaders=), not by
   =MailComposer=, so =message/build= adds them itself (=build-wire=, ="1 (Highest)"= /
   ="High"= / ="High"= etc., merged under the user's =:headers=). (b) mailparser never sets a
   top-level =priority= (6.1 was wrong): the priority family is folded into ONE headers
   entry keyed =priority= (6.3 was right) — the parsed map reads it from there
   (=:priority :high|:normal|:low=, =:normal= when absent) and =(message/header m
   "priority")= is ="high"= while =X-Priority= itself is absent from =:headers= (still
   present in =:header-lines=).
5. *Header names in the parsed map are canonical-cased strings* (="X-Custom-Header"=,
   ="Message-ID"=, ="MIME-Version"= — =message/canonical-header-name=, acronym table
   =header-acronyms=), not the lower-case mailparser keys 14.1 / 14.3 showed; =message/header=
   looks them up case-insensitively. Address headers inside =:headers= are the same
   =[{:name :address}]= vectors as the top-level fields (mailparser's ={value html text}=
   wrapper is dropped); groups are flattened into their members tagged =:group "Team"=.
6. *mailparser's 'now' for an unparseable Date:* (12.5) is detected: the raw =Date:= line is
   re-parsed (=parse-binding/parse-date-iso=) and the parsed map reports =:date nil= +

   nil.
